Should a new PerformanceObserver with buffered:true require buffered entries synchronously?

  • Michal: Some perf entries are full page lifecycle and continue to get emitted forever.
  • … not 100% consistent, e.g. resource Timing
  • … So instead of polling in a loop, you should use performance observer and get notifications
  • … “buffered” flag gives you a list from the performance timeline and give it to the observer
  • … But the spec is that as soon as you construct your PO we copy the list and queue an observer.
  • … There’s also a takeRecords call
  • … So you can polyfill getEntriesByType using performance observer, which gives you the entries synchronously
  • … used this in an observer when wanting to snapshot the last set of entries
  • … The actual scheduling of the initial callback has some unique behaviors
  • … The first callback will only be all the previously buffered entries and the next will contain followups
  • … There may be expectation to only see old values before seeing new ones?
  • … Questions:
  • … 1. Is this a spec oversight?
  • … 2. Is this behavior relied on?
  • … A recent example for complexity - to support scroll timing with buffered, the browser needs to do all the book keeping, but can we be lazy and only create the entries once the page needs the entries?
  • … You kinda can’t at the moment due to the sync nature
  • Nic: After you take the initial buffer, a second call won’t get the entries?
  • Michal: Every new observer gets the full list, but the callback will get called once for the old entries, and again for the new ones
  • … Normally we’d cluster entries, but that doesn’t happen in that first callback
  • Barry: The whole book keeping thing, you still get all the entries, right?
  • Michal: Today the only entries you’d get with buffered: true are the ones that are already in the timeline. The browser has to do the book-keeping, but we can be lazier with constructing the performance entry.
  • … Once you register your first PO, we have to construct, but not before
  • … With Scroll Timing, that info is stored in the compositor.
  • Barry: But there are no guarantees for a performance observer RE when it’d be emitted
  • Michal: I guess the spec doesn’t guarantee that, but I doubt anyone implements it that way
  • … I don’t know how existing users of PO would handle such a change
  • Barry: My personal preference is that getEntriesByType is supported everywhere
  • Michal: At the moment you can polyfill this, but it will break if we change that. Today takeRecords has to return something, but it could return nothing if we didn’t construct the entries
  • … Currently specified to queue sync and I suggest to change to async
  • Scott: Order is not guaranteed, but people may rely on it
  • NoamH: Trying to understand the sync nature
  • Michal: Queues the task sync, not the callback
  • … If we have entries in the buffer, they need to be copied immediately
  • … Can say that implementations can construct entries async 
  • NoamH: The tricky part would be takeRecords. Challenge is not breaking this
  • Michal: takeRecords is used a lot at page unload. But we know in the past that the perf timeline can be mid-measurement, even if you call takeRecords
  • NoamH: So people use it at beforeUnload and collect whatever is already there. Can’t break takeRecords
  • Michal: Just suggesting to extend the initial gap, not break takeRecords
  • Bas: The case where it might matter, is on page hide
  • Michal: So you won’t be able to register new POs at page hide
  • Nic: As long as you register your PO first you’d be OK
  • Yoav: I’m sure people are relying on this, but how much is an interesting question.
  • … ScrollTiming is one of the first where you’re collecting measurements at compositor, then when a PO is registered, it’s an IPC call away
  • … We could optimistically move that data to the renderer, but it’s extra work
  • Bas: And usually wasteful
  • Yoav: What we could do here is just change that initial gap for this specific entry, where no one is relying on it right now, and not worry about compat, change the spec so that people won’t read the spec and rely on it
  • Michal: PT could be left as-is
  • … Other APIs could have some sort of <meta> tag to opt in, notify RUM so that it can be loaded later
  • Bas: We limit the amount of entries that are buffered
  • … General, no guarantees about synchronicity, in any specs
  • … I think spec-wise you’re already good?
  • Michal: What is the true interop, and expectations?
  • Barry: Found some examples in Github searches
  • Yoav: Decent hint we can do this for new entries, but maybe not back-port back
  • … Value to providing measurements synchronously
  • Bas: Then you should just be able to use getEntriesForType()
  • Barry: Point was it was a footgun for metrics to be measured any point in time
  • … We’ve taken you can’t get LCP after 5 seconds because browser knows better
  • Yoav: At some point we decided all new things should be PO-only
  • … Principled stance
  • … If there’s significant costs to entry-creation or book-keeping (like moving data from compositor to renderer), it should be async
  • Bas: What’s reason for Scroll Timing to support buffered at all?
  • Michal: We don’t want scripts to load as early as possible and slow down loading
  • … Incentivize not slowing down loading performance
  • Bas: OTOH you incentivize browsers to do book-keeping regardless
  • Michal: Very rarely-used feature which has high overhead?  Or can browser do it efficiently enough that it doesn’t affect typical user?
  • … CWV we measure anyway, so they’re as efficient as possible
  • … Question of exposing to developer as an opt-in isn’t much of a lift

Paint Timing

  • … But content-length is TAO-protected.
  • … Since the developer controls the layout size of the image, they can effectively binary search and find the bytes of the image
  • … We’re clamping it by intrinsic size, but here we’re downscaling it to find the size
  • … Altering the size of the layout to get the content length of the image - same image over time
  • … The image would have to be visible
